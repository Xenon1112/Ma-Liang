# 「马良」插件化改造计划书

> 配套文档:`docs/插件化架构设计.md`(架构与协议设计,下称"设计文档")。
> 设计文档回答"做成什么样",本文档回答"分几步做、每步交付什么、怎么验收"。
>
> **项目目标**:将单体架构演进为「极简内核 + 一切皆插件」,支撑第三方插件生态,让创作者通过插件定制自己的写作平台。第一个完整第三方形态参考实现为 MuseScore 集成(现 `score_service`)。

---

## 1. 范围

### 1.1 范围内

- 内核抽取:HTTP 层、数据库连接与迁移框架、配置、事件总线、插件管理器、插件 API
- 全部 17 个现有功能模块插件化(含各自 schema 迁移归属、前端组件迁移)
- 前端 `NW` 命名空间 + manifest 驱动加载 + 扩展点机制(设计文档 §7.4)
- 第三方插件支持:用户数据目录加载、待启用流程、设置页插件管理
- 插件协议:v0 草案 → v1.0 定稿,含符合性测试
- 开发者体验:插件脚手架、`--dev` 模式、《第三方插件开发指南》
- 存量用户数据无损迁移(legacy_bootstrap)

### 1.2 范围外(明确不做)

- 插件沙箱/权限强制(Python 同进程做不到,如实文档化)
- 插件市场/远程分发(安全模型撑不住;分发走目录拷贝 → zip 安装)
- 插件独立进程运行
- 业务功能本身的新增或改版(改造期间冻结新功能,避免边拆边改)

### 1.3 可选后续(本期不做,预留接口)

- **插件独立更新通道**:内置插件首启释放到用户数据目录、按版本单独更新、`min_core_version` 校验。约 2–3 人日,等生态有真实需求后启动(设计决策见 §6)。

---

## 2. 总体策略

1. **应用全程可用**:每个阶段结束都是可发布状态,不搞长期分支;
2. **行为不变优先**:阶段 0/1 原则上不改变任何用户可感知行为,只动结构;
3. **协议晚冻结**:v0 草案随阶段 1 产出并明确"未冻结",经 MuseScore 参考实现验证后才发布 v1.0;
4. **逃生门机制**:迁移期用 legacy 路由直通 + 前端全局别名兜底,逐插件切换、逐个拆除;
5. **双验证**:每阶段同时验证 `uv run python app.py --browser` 开发形态与 PyInstaller 打包产物。

---

## 3. 阶段计划

### 阶段 0 — 内核骨架(纯移动,行为不变)

**任务**

- `miniframe.py` → `core/httpd.py`;`database.py` → `core/database.py`;`services/config_service.py` → `core/config.py`
- 调整全部 import;`app.py` 保留路由与启动逻辑不变
- 修复三个 spec 文件漏列 `services.score_service` 的问题

**交付物**:`core/` 目录存在,应用行为与改造前完全一致。

**验收**:全功能手工回归通过;打包产物验证通过。

**预估**:1–2 人日。

---

### 阶段 1 — 插件框架 + 试点插件 + 协议 v0 草案

**任务**

- 实现 `core/plugin_manager.py`(扫描、manifest 校验、拓扑排序、`SourceFileLoader` 加载、故障隔离)
- 实现 `core/plugin_api.py`(route / db / config / on / emit / provide / require)
- 实现 `core/events.py` 后端事件总线
- 实现插件化迁移框架:`plugin_migrations` 表 + 每插件独立迁移序列 + 存量用户 `legacy_bootstrap`
- 迁移试点插件:`inspiration`、`world_setting`(最简单、零依赖)
- 前端:`NW` 命名空间、manifest 驱动加载(仅对试点插件生效,其余维持旧 script 标签)、全局别名兼容层
- 撰写《插件协议 v0 草案》(标注"未冻结"),目录:manifest 规范 / PluginAPI / 事件目录 / 扩展点 / 命名约束 / 版本策略
- 编写**协议符合性测试**:fixture 插件,断言注册路由、建表、迁移、收发事件全链路(同时填补项目无自动化测试的关键空白)

**交付物**:框架可用;两个试点插件按完整协议运行;协议 v0 草案;符合性测试接入。

**验收**:试点插件功能回归通过;禁用某试点插件后应用其余功能不受影响;第三方目录手工放入一个 hello-world 插件可加载。

**预估**:3–5 人日。**这是全项目风险最高的一步**,协议设计问题应在此阶段暴露。

---

### 阶段 2 — 主干业务插件化

**任务**(按依赖序,每个插件为一个独立提交单元)

1. `project` → 2. `chapter`、`draft`、`outline` → 3. `character`、`search`、`recycle` → 4. `export`、`json_transfer` → 5. `backup`
- 每迁一个:拆路由出 `app.py`、schema 迁移归位、前端组件挂到 `NW.plugins.<id>`、删对应全局别名
- 在 `export`/`json_transfer` 一步用 `provide/require` 消除 `_resolve_output_path` 私有引用
- `app.py` 随迁移逐步瘦身为 `core/kernel.py` 启动壳

**交付物**:9 个插件完成迁移;`app.py` 消失。

**验收**:每个插件迁移后即时回归;全部完成后整体回归 + 打包验证。

**预估**:8–12 人日(单体工作量最大,但单步风险低,纯体力劳动为主)。

---

### 阶段 3 — 复杂插件 + MuseScore 参考实现

**任务**

- 迁移 `script`、`floating_song`(V2–V5 schema 归位)
- 迁移 `score`(MuseScore 集成,V6 schema、`musescorePath` 配置、外部二进制调用)——**作为第一个覆盖协议全部维度(迁移/配置/外部依赖/前端组件)的参考实现**
- 以 score 插件为示例撰写《第三方插件开发指南》
- 根据本阶段实际暴露的问题修订协议草案(API 顺手程度、事件时机、扩展点缺口)

**交付物**:全部 17 个功能完成插件化;开发指南初稿;协议修订记录。

**验收**:剧本/音乐剧/乐谱功能完整回归;MuseScore 实际调起验证;打包产物验证。

**预估**:3–5 人日。

---

### 阶段 4 — 生态开放

**任务**

- 设置页插件管理界面:内置/第三方插件列表、第三方插件"待启用"流程、manifest 信息展示、加载失败原因显著暴露
- 第三方插件安全提示:启用前明确告知"插件拥有完整应用权限"
- 插件脚手架:`plugin.json` + 最小 `backend.py` + 一个前端组件的模板,一条命令生成
- `--dev` 模式:开发中插件改动后重启即重载,免重打包
- 发布《插件协议 v1.0》:基于阶段 1–3 验证结果定稿,承诺语义化版本与废弃周期(废弃 API 至少保留一个大版本)
- zip 插件包 + 设置页"安装插件"按钮(分发第二步)

**交付物**:第三方开发者可凭协议 v1.0 + 指南 + 脚手架独立开发并安装插件。

**验收**:用一个全新插件(非团队成员视角)走完"脚手架生成 → 开发 → zip 打包 → 设置页安装 → 启用 → 使用"全流程。

**预估**:3–5 人日。

---

### 阶段 5 — 清理

**任务**

- 移除 legacy 路由直通、前端全局别名、`legacy_bootstrap` 对新装用户的判定代码
- 文档收尾:README、新手教程涉及结构的部分更新

**预估**:1–2 人日。

---

### (可选)阶段 6 — 插件独立更新通道

触发条件:生态出现真实的第三方插件,或内置插件有独立于应用发版的更新需求。

- 内置插件首启释放至用户数据目录,之后按版本号单独覆盖更新
- 更新清单(本地/远程 JSON)+ zip 下载替换
- 插件更新前校验 `min_core_version`,不满足则引导升级应用本体

**预估**:2–3 人日。

---

## 4. 里程碑

> 变更(阶段 2 完成后):插入「阶段 2.5 低耦合改造」(见 `docs/低耦合改造计划书.md`),
> 消灭 recycle/json_transfer/app.js 三处结构性耦合;阶段 3(MuseScore 参考实现)顺延,协议 v1.0 冻结相应顺延。

| 里程碑 | 内容 | 完成标志 |
|---|---|---|
| M1 | 内核骨架(阶段 0) | 行为不变的结构重组完成 |
| M2 | 框架跑通(阶段 1) | 试点插件运行 + 协议 v0 草案 + 符合性测试 |
| M2.5 | 低耦合(阶段 2.5) | 测试插件不改现有文件即可接入回收站/导出/侧边栏/工具栏/事件 |
| M3 | 单体消失(阶段 2 末) | `app.py` 只剩启动壳 |
| M4 | 全量插件化(阶段 3) | 17/17 插件化,MuseScore 参考实现落地 |
| M5 | 生态开放(阶段 4) | 协议 v1.0 发布,第三方全流程走通 |

总预估:**21–32 人日**(单人、不含新功能开发)。阶段间可随时暂停,每个里程碑都是可发布状态。

## 5. 风险与应对

| 风险 | 等级 | 应对 |
|---|---|---|
| 阶段 1 协议设计失误,后期返工 | 高 | 试点+MuseScore 双重验证后再冻结 v1.0;`api_version` 预留演进;符合性测试兜底 |
| 中间态前后端两套加载并存期间出现诡异 bug | 中 | 逃生门机制;逐插件切换、即时回归;每插件独立提交可单独回滚 |
| 项目无自动化测试,回归靠手工 | 中 | 阶段 1 借机建立符合性测试;每阶段维护手工回归清单 |
| 110 个路由 URL 变更影响用户书签/外部引用 | 低 | 迁移期 legacy 直通,阶段 5 才拆除 |
| 第三方插件安全事件(恶意插件伤用户) | 中 | 默认不启用 + 显式权限警告;文档不宣传"安全";分发渠道可控 |
| 改造期间与日常 bug 修复冲突 | 中 | 冻结新功能;bug 修复随所在插件迁移节奏处理 |
| 工作量低估(前端 3600 行无框架代码的迁移最易低估) | 中 | 阶段 2 预估已留余量;前端组件迁移以"挂命名空间+别名"为最小动作,不顺手重构 |

---

## 6. 关键设计决策记录(本计划依赖的前提)

1. **插件化买的是生态契约,不是代码简化**——内核 400~500 行是必要开销,不做运行时卸载等过度设计;
2. **内置与第三方同协议**,无特权;
3. **协议三件套**:文档 + 加载器强制校验 + 符合性测试,缺一不可;
4. **"只动插件不动内核"在开发层面由边界设计保证;交付层面(用户侧插件独立更新)为可选阶段 6**,需 `min_core_version` 校验配套;
5. **MuseScore 是协议成熟度的试金石**,v1.0 冻结以它为前置条件。

---

## 7. 成功度量

- `core/` 在发版 diff 中的占比随里程碑持续走低(M4 后单次发版应 < 20%);
- 阶段 4 后,新增功能默认以新插件形式交付,不改内核;
- 第三方插件(含 MuseScore 形态的外部工具接入)仅依赖协议文档即可开发,无需阅读内核源码。
