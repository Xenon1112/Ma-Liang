# 「马良」写作工具 —— 一切皆插件架构设计

> 目标:将现有单体架构重构为「极简内核 + 一切皆插件」模式,核心只保留 HTTP、数据库连接、插件管理和事件总线,全部业务功能(章节、角色、导出、剧本、乐谱……)都是可插拔插件,并支持用户数据目录加载第三方 `.py` 插件。

---

## 1. 现状评估:为什么这个项目适合插件化

现有代码库的结构意外地接近插件化的前置条件:

| 现状 | 对插件化的意义 |
|---|---|
| 17 个 service 全是模块级纯函数,几乎只依赖 `database.py` | 天然就是插件粒度,无需拆类、无需引入 DI 容器 |
| `miniframe.Flask.route()` 本质是往 `self.routes` 列表 append | 路由注册机制现成,任何对象都能注册路由 |
| 前端 `AppState` 已有极简 on/emit 事件总线 | 前端插件通信机制现成 |
| `index.html` 用 24 个 `<script src>` 标签顺序加载 | 改成 manifest 驱动的动态加载成本低 |
| 已有 `get_user_data_dir()`(app.py:21 附近处理 `_MEIPASS`) | 第三方插件的存放位置现成 |

**主要障碍**(必须在设计中解决):

1. `app.py` 单文件平铺约 110 个路由,需改为插件自注册;
2. `json_transfer_service` 引用了 `export_service._resolve_output_path` 私有函数——插件间不能跨边界摸内部实现;
3. 数据库迁移写死在 `database.py` 的 `MIGRATION_V1..V6` 列表,插件化后 schema 归各插件所有;
4. PyInstaller frozen 模式下 `sys.path` 指向 PYZ 归档,外部插件必须用 `SourceFileLoader` 从磁盘绝对路径加载;
5. 前端组件靠全局名互调(`ProjectList`、`Editor` 等),无注册表。

## 2. 目标架构总览

```
novel-writer/
├── core/                       # 内核(唯一不可卸载的部分)
│   ├── __init__.py
│   ├── kernel.py               # 启动流程:init_db → 加载插件 → run server → pywebview
│   ├── httpd.py                # 现 miniframe.py 原样迁入(Flask shim)
│   ├── database.py             # 连接管理 + 插件化迁移框架(见 §5)
│   ├── config.py               # 现 config_service 迁入 + 插件配置 schema 支持
│   ├── events.py               # 后端事件总线(插件解耦的关键)
│   ├── plugin_manager.py       # 发现、校验、加载、卸载、依赖排序
│   └── plugin_api.py           # 暴露给插件的稳定 API 表面(见 §4)
│
├── plugins/                    # 内置插件(随应用打包,结构与第三方插件完全相同)
│   ├── project/
│   │   ├── plugin.json         # manifest
│   │   ├── backend.py          # service 逻辑 + 路由注册
│   │   ├── migrations/         # 本插件拥有的 schema 演进
│   │   │   ├── 001_init.sql
│   │   │   └── 002_add_xxx.sql
│   │   └── web/
│   │       ├── api.js          # 前端 API 封装(挂到命名空间)
│   │       └── components.js   # UI 组件
│   ├── chapter/
│   ├── draft/
│   ├── outline/
│   ├── character/
│   ├── world_setting/
│   ├── inspiration/
│   ├── search/
│   ├── export/
│   ├── json_transfer/
│   ├── backup/
│   ├── recycle/
│   ├── script/
│   ├── floating_song/
│   └── score/
│
└── <用户数据目录>/
    └── plugins/                # 第三方插件,结构同内置插件
        └── my_plugin/
            ├── plugin.json
            ├── backend.py
            └── web/...
```

**设计原则:**

- **内核不知道任何业务**。内核不认识"章节""角色"这些概念,它只提供:HTTP 服务、路由注册表、SQLite 连接、迁移执行器、配置存取、事件总线、插件生命周期管理。
- **内置插件与第三方插件走完全相同的协议**。内置插件只是"打包进发行版、放在 `plugins/` 目录"的插件,没有任何特权。这保证插件协议是真协议,不是摆设。
- **每个插件自包含**:自己的路由、自己的表、自己的迁移、自己的前端组件、自己的配置键。

## 3. 插件协议

### 3.1 manifest(`plugin.json`)

```json
{
  "id": "chapter",
  "name": "章节管理",
  "version": "1.0.0",
  "api_version": 1,
  "dependencies": ["project"],
  "optional_dependencies": ["draft"],
  "entry": "backend.py",
  "web": ["web/api.js", "web/components.js"],
  "config_schema": {
    "chapter.autoSaveInterval": { "type": "int", "default": 30 }
  },
  "min_core_version": "2.0.0"
}
```

字段说明:

- `id`:全局唯一,目录名必须与其一致;同时是**命名空间**——路由前缀、表名前缀、配置键前缀、前端命名空间全部由它派生。
- `api_version`:插件面向的内核 API 版本。内核升级 API 时递增,加载器据此拒绝不兼容插件。
- `dependencies`:硬依赖,缺失则本插件不加载;`optional_dependencies`:有则排在其后加载,无则跳过。
- `web`:前端资源,由内核按依赖序拼进页面(替代现在的 24 个手写 script 标签)。
- `config_schema`:插件声明自己的配置键,自动并入全局配置(键名强制 `<id>.` 前缀)。

### 3.2 后端入口约定

`backend.py` 必须导出一个 `Plugin` 类(或 `create_plugin()` 工厂),实现生命周期钩子,全部可选:

```python
class Plugin:
    def activate(self, api): ...   # 注册路由、订阅事件、声明服务
    def deactivate(self): ...      # 卸载时清理(内置插件一般用不到)
    def on_project_open(self, project_id): ...  # 订阅内核/其他插件事件的示例
```

### 3.3 命名空间硬约束(加载器强制校验)

| 资源 | 约束 | 示例(chapter 插件) |
|---|---|---|
| 路由 | 必须以 `/api/plugins/<id>/` 开头 | `/api/plugins/chapter/list` |
| 表名 | 必须以 `<id>__` 开头 | `chapter__chapters` |
| 配置键 | 必须以 `<id>.` 开头 | `chapter.autoSaveInterval` |
| 前端全局 | 只允许挂在 `NW.plugins.<id>` 下 | `NW.plugins.chapter.Editor` |

> 关于路由前缀:为了**不破坏现有前端**,迁移期可以在 manifest 里声明 `"legacy_routes": true`,允许插件注册无前缀的旧路由(`/api/chapters` 等),由内核做冲突检测;全部前端改造完成后移除该逃生门。这是兼容性与架构纯粹性之间的务实妥协,建议保留。

## 4. 插件 API(`core/plugin_api.py`)

插件拿到的是 `api` 对象,**这是插件唯一允许接触的边界**,也是内核承诺稳定的版本化表面:

```python
class PluginAPI:
    # HTTP
    def route(self, rule, **opts): ...        # 等价现在的 @app.route,自动加前缀和校验

    # 数据
    def db(self) -> Connection: ...           # 每请求新连接,用法与现 get_conn() 相同
    def row_to_dict(self, row): ...

    # 配置
    def get_config(self, key, default=None): ...
    def set_config(self, key, value): ...

    # 事件(后端总线)
    def on(self, event: str, handler): ...
    def emit(self, event: str, **payload): ...

    # 服务注册表 —— 解决插件间调用
    def provide(self, name: str, service: dict): ...   # 声明"我对外提供这些函数"
    def require(self, name: str) -> dict | None: ...   # 消费别的插件的服务,缺失返回 None

    # 前端资源
    # (由 manifest.web 声明,无需代码)
```

**关键决策:用 `provide/require` 服务注册表替代现在的直接 import。** 以现有的违规引用为例:

```python
# export 插件 activate 时:
api.provide("export", {"resolve_output_path": _resolve_output_path, "export_txt": ...})

# json_transfer 插件使用时:
export = api.require("export")   # export 在 dependencies 里,保证已加载
path = export["resolve_output_path"](...)
```

规则:插件间只允许通过 `require` 拿到的公开字典交互,**禁止 import 其他插件的内部模块**(加载器可用 `sys.modules` 审计,或在 code review 层面约束;Python 无法硬隔离,约定 + manifest 依赖声明即可)。

### 事件总线承载横向联动

不直接依赖的场景走事件,例如:

- `chapter` 发出 `chapter.deleted`,`recycle` 订阅后写入回收站,`search` 订阅后清索引;
- `project.opened` 由 project 插件发出,所有关心当前项目的插件订阅。

事件名约定 `<plugin_id>.<动作>`,内核不做注册限制,但文档化在内核里。

## 5. 数据库:插件化迁移框架

现有 `MIGRATION_V1..V6` + `db_version` 表是全局单序列,插件化后改为**每个插件独立的迁移序列**:

```sql
-- 内核拥有的唯一两张业务无关表之外的元表
CREATE TABLE IF NOT EXISTS plugin_migrations (
    plugin_id   TEXT NOT NULL,
    version     INTEGER NOT NULL,
    applied_at  TEXT NOT NULL,
    PRIMARY KEY (plugin_id, version)
);
```

- 内核加载插件时,扫描其 `migrations/*.sql`(文件名 `NNN_description.sql`,按序号排序),对比 `plugin_migrations` 表,**在该插件 activate 之前**应用未执行的迁移。
- 迁移在事务中执行,失败则插件标记为加载失败,不影响其他插件。
- 现有 V1–V6 的归属拆分:V1 主体归 `project`/`chapter`/`character` 等各自插件的 `001_init.sql`;V2–V3 归 `script`;V4–V5 归 `floating_song`;V6 归 `score`。
- **存量用户迁移**:内核保留一次性的 `legacy_bootstrap`:检测到旧 `db_version` 表且为 V6 时,把各插件的 `plugin_migrations` 标记为已应用到对应版本;迁移 SQL 一律 `IF NOT EXISTS` 幂等,存量库上照常执行(已有表是 no-op),以保证后加的内置插件也能建出表。这是一次性代码,迁移完即不再触发。
- 软删除工具(`soft_delete`)、`next_sort_order` 等通用 helper 上移到 `core/database.py`,通过 `api.db_helpers` 暴露。

## 6. 插件发现、加载与第三方插件支持

### 6.1 加载流程(`core/plugin_manager.py`)

```
1. 扫描两个插件源:
   a. 内置:打包目录下 plugins/(frozen 时位于 sys._MEIPASS/plugins)
   b. 第三方:get_user_data_dir()/plugins/
2. 读取并校验每个 plugin.json(id 唯一、api_version 兼容、字段合法)
3. 拓扑排序(dependencies / optional_dependencies),循环依赖 → 报错并跳过整环
4. 按序对每个插件:
   a. 应用 migrations(§5)
   b. SourceFileLoader 从磁盘绝对路径加载 entry(见 6.2)
   c. 实例化 Plugin,调用 activate(api) —— api 是绑定了该插件 id 的 PluginAPI
   d. 任何异常:记录日志、标记 failed,继续加载其余插件(故障隔离)
5. 收集所有 manifest.web,按加载序生成前端资源清单(见 §7)
6. 启动 HTTP 服务
```

### 6.2 第三方插件的动态加载(PyInstaller 兼容)

frozen 模式下 `sys.path` 指向 PYZ 归档,普通 import 无法加载外部 `.py`,必须:

```python
import importlib.util
spec = importlib.util.spec_from_file_location(f"nw_plugin_{pid}", entry_path)
module = importlib.util.module_from_spec(spec)
spec.loader.exec_module(module)
```

这条路径在 PyInstaller 下可行,但有一个必须写进文档的限制:**第三方插件只能依赖标准库 + 内核通过 `api` 暴露的能力,不能依赖发行版未打包的三方包**(frozen 环境里没有)。如果未来要支持插件带依赖,方案是把插件格式升级为 zip 包并内置其 `site-packages`,本期不做。

### 6.3 安全边界(必须如实告知用户)

Python 插件是**同进程执行任意代码**,没有沙箱。第三方插件拥有整个应用的权限(读写数据库、文件系统、网络)。缓解措施只能是外围的:

- 第三方插件默认**不自动启用**:首次发现时列入"待启用"清单,需用户在前端设置页显式开启;
- manifest 中声明 `"permissions": ["filesystem", "network"]` 之类的意图清单,前端展示给用户(纯声明式,无法强制,但提供决策依据);
- 插件加载失败隔离(6.1-4d)保证坏插件不拖垮应用。

### 6.4 打包调整

- spec 文件:`datas` 增加整个 `plugins/` 目录;**删掉手写的 services hiddenimports**(改为插件后静态 import 链断裂,hiddenimports 也不再需要,因为插件是数据文件 + 运行时加载);
- 顺带修复现有三个 spec 漏列 `services.score_service` 的问题(该问题在插件化后自然消失);
- onefile 模式下 `sys._MEIPASS` 只读,第三方插件必须且只能放 `get_user_data_dir()/plugins/`,与 DB 同侧。

## 7. 前端插件化

现状:无构建工具,24 个 script 标签全局加载,组件靠全局名互调。

### 7.1 加载机制

- `/` 页面由内核渲染:模板里不再手写 script 标签,改为注入插件管理器产出的资源清单(按插件拓扑序):
  ```html
  <script src="/api/plugins/registry"></script>  <!-- 输出 NW.pluginRegistry = {...manifest 信息} -->
  <!-- 然后按序输出每个插件的 web 资源: -->
  <script src="/plugins/chapter/web/api.js"></script>
  ```
- 内核增加 `/plugins/<id>/<path>` 静态路由,从对应插件目录(内置或用户目录)serve 文件。
- 保留现有 `?v=` 缓存戳机制,值改用插件 version + 内核版本。

### 7.2 命名空间与注册表

- 内核 JS(`static/js/core/`)提供唯一全局 `NW`:
  ```js
  NW.plugins = {};                 // 插件挂载点:NW.plugins.chapter = {...}
  NW.events  = AppState.events;    // 现有事件总线,原样保留
  NW.registerComponent(name, fn);  // 组件注册表(侧边栏条目、设置页面板等扩展点)
  ```
- 现有组件从全局名(`ProjectList`、`Editor`)迁移到 `NW.plugins.<id>` 命名空间下;组件间的直接互调改为 `NW.registerComponent` 注册的**扩展点**:
  - 侧边栏:每个插件注册 `sidebar.entries`;
  - 设置页:每个插件注册 `settings.panels`(配合 §3.1 的 config_schema 可半自动生成);
  - 编辑器工具栏按钮、导出格式等,同理各是一个扩展点。
- **迁移期兼容**:内核 JS 里留一层 `window.ProjectList = NW.plugins.project.List` 之类的别名,逐插件迁移、逐个删除,避免一次性改 3600 行前端。

### 7.3 第三方插件的前端

- 与后端同源 serve,无额外机制;
- 设置页提供插件管理界面:列表、启用/禁用、查看 manifest;
- 第三方 JS 同样无沙箱,与 6.3 同一信任模型。

### 7.4 前端扩展点清单(生态定制能力的基础)

「创作者定制自己的写作平台」要求插件能改 UI,扩展点是一等公民,不是迁移的副产品。首版扩展点:

| 扩展点 | 注册方式 | 用途示例 |
|---|---|---|
| `sidebar.entries` | `NW.registerComponent("sidebar.entries", {...})` | 插件在左侧导航加入口(如"乐谱库") |
| `editor.toolbar` | 同上 | 编辑器工具栏按钮(如"插入乐谱引用") |
| `editor.panels` | 同上 | 编辑器侧栏面板(如"角色卡""歌词板") |
| `settings.panels` | 同上 | 设置页面板(配合 config 前缀机制) |
| `export.formats` | 同上 | 注册新导出格式(如 MusicXML) |
| `themes` | manifest 声明 CSS 文件 | 界面主题 |

扩展点清单本身也版本化,随 `api_version` 演进;新增扩展点向后兼容,废弃走与后端 API 相同的废弃周期。

## 8. 配置系统

- `core/config.py` 由现 `config_service` 迁入,`DEFAULTS` 不再是单一硬编码字典,改为:内核 DEFAULTS + 各插件 `config_schema` 声明的默认值**合并**而成;
- 存储仍是 `app_config` 表(内核所有),键强制 `<plugin_id>.` 前缀;`get_config("musescorePath")` 这类现存的无前缀键迁移为 `score.musescorePath`,legacy 键在迁移期做一次读取兼容;
- `/api/config` 路由归内核,返回合并视图;插件只通过 `api.get_config` 读自己的键。

## 9. 迁移路线图

按"每一步都可独立交付、应用始终可用"的原则排序:

**阶段 0 — 内核骨架(不改动任何业务行为)**
1. `miniframe.py` → `core/httpd.py`,`database.py` → `core/database.py`,`config_service` → `core/config.py`,调整 import。纯移动,行为不变,全量回归。

**阶段 1 — 插件框架 + 试点**
2. 实现 `plugin_manager` / `plugin_api` / 事件总线 / `plugin_migrations` 表 / legacy_bootstrap。
3. 迁移两个最简单、零依赖的插件:`inspiration`、`world_setting`(各自 46–48 行,适合验证协议)。
4. 前端实现 `NW` 命名空间 + manifest 驱动加载(对这两个插件生效,其余仍走旧 script 标签)。

**阶段 2 — 主干业务插件化(按依赖序)**
5. `project`(无依赖)→ `chapter`、`draft`、`outline`(依赖 project)→ `character`、`search`、`recycle` → `export`、`json_transfer`(在此步用 `provide/require` 解决 `_resolve_output_path` 私有引用)→ `backup`。
6. 每迁完一个插件,删除 `app.py` 中对应路由节和 import;`app.py` 逐步瘦身为 `core/kernel.py` 的启动壳。

**阶段 3 — 复杂插件(生态参考实现)**
7. `script`、`floating_song`、`score`(这三个带有最多的表迁移和前端组件,V2–V6 的 schema 在此归位)。
8. **其中 `score`(MuseScore 集成)是生态的第一个完整参考实现**:它自带迁移(V6)、自带配置(`musescorePath`)、调外部二进制、有前端组件,覆盖插件协议的所有维度。迁完后以它为示例撰写《第三方插件开发指南》——一个真实的、有外部依赖的插件比玩具 demo 更能暴露协议设计问题。

**阶段 4 — 第三方插件开放(生态启动)**
9. 设置页插件管理界面:列表、待启用流程、查看 manifest。
10. 开发者体验:插件模板/脚手架、`--dev` 模式(插件改动免重打包,仅重启即重载)、《第三方插件开发指南》。
11. API 稳定性承诺落地:`plugin_api` 语义化版本化,变更日志,废弃 API 至少保留一个大版本。
12. 前端扩展点清单定稿并文档化(见 §7.4)。

**阶段 5 — 清理**
9. 移除 legacy 路由别名、前端全局别名、`legacy_bootstrap` 标记为只对新装用户跳过。

每阶段结束的标准:应用可启动、该阶段涉及的插件功能手工回归通过、`uv run python app.py --browser` 与 PyInstaller 打包产物均验证。

## 10. 风险与权衡

| 风险 | 评估 | 缓解 |
|---|---|---|
| 中间态前后端两套加载机制并存 | 阶段 1–3 必然存在 | 以 manifest 的 `legacy_routes` 和前端别名为逃生门,逐个插件切换,每步可回归 |
| 插件协议设计失误,后期改协议代价大 | 中 | 阶段 1 用两个试点插件验证协议;`api_version` 字段预留演进空间 |
| 第三方插件无沙箱 | 高(架构本质) | 如实文档化;默认不启用 + permissions 声明;绝不宣传为"安全扩展" |
| 110 个路由的 URL 变更破坏前端/用户书签 | 中 | 迁移期 legacy 路由直通,前端切完后统一加前缀并保留重定向 |
| 故障隔离后功能静默缺失 | 低 | 插件加载失败在前端设置页和启动日志显著暴露 |
| 工作量 | 后端 ~4000 行 + 前端 ~3600 行重排,迁移机制与回归测试另计 | 分五阶段,每阶段独立可交付;阶段 0/1 即产出大部分架构价值 |

## 11. 定位说明:为什么做、做到哪

**本项目做插件化的理由是生态,不是简化。** 插件化不会减少代码量(内核 400~500 行是纯开销),它买的是三样生态必需品:稳定契约(`plugin_api` 版本化)、明确边界(表/路由/配置/UI 都有归属)、外部可扩展(第三方无需改主程序)。项目目标是「让创作者通过插件定制自己的写作平台」,这三样缺一不可。

本设计达成「一切皆插件」模式的三个核心特征:

1. **内核极简且业务无关**——`core/` 里没有任何"章节/角色/导出"的概念;
2. **内置与外部同协议**——内置插件只是预装的插件,协议无特权,MuseScore 集成是第一个完整参考实现;
3. **一切通过显式接口交互**——路由、配置、表、服务、事件、前端扩展点全部有归属和边界。

有意未采纳的部分:插件不跑在独立进程/环境里(Python 桌面单机应用无此必要,代价远大于收益);无插件市场/远程安装(安全模型撑不住,分发走目录拷贝 → zip 包安装两步);插件无沙箱(如实文档化,信任交给用户的显式启用动作)。
