# 低耦合改造计划书(插件化阶段 2.5,插队在阶段 3 之前)

> 背景:阶段 2 完成后,代码级耦合已清零(插件间无 import,全走 provide/require),
> 但仍有三个结构性耦合点。本计划把它们消灭到「新增插件不需要修改任何现有代码」。
> 配套:`docs/插件化架构设计.md`、`docs/插件协议-v0草案.md`。
> MuseScore(score 插件)参考实现推迟到本计划之后,协议 v1.0 冻结相应顺延。

## 目标(验收标准)

**一个符合协议的第三方插件,不改动任何现有文件,就能做到:**

1. 它的实体表进入回收站(软删除可见、可恢复、到期清理);
2. 它的表进入整项目 JSON 导出/导入;
3. 它的面板出现在右侧资料栏,它的按钮出现在工具栏;
4. 它收到项目切换等生命周期事件。

反过来:**recycle、json_transfer、app.js 不认识任何具体插件。**

---

## 现状:三个耦合点(证据)

| # | 耦合点 | 位置 | 问题 |
|---|---|---|---|
| C1 | 实体表清单硬编码 | `plugins/recycle/backend.py` 的 `ENTITY_TABLES` | 新插件的表进不了回收站 |
| C2 | 导出/导入表清单硬编码 | `plugins/json_transfer/backend.py` | 新插件的表不被导出;导入的 id 重映射逻辑绑死已知表 |
| C3 | app.js 全知编排 | `static/js/app.js` 直接引用 11 个组件全局名(`ProjectList`/`SearchPanel`/`Editor`/`OutlinePanel` 等) | 新插件的 UI 必须改 app.js 才能接入 |

过渡态耦合(window 兼容别名、legacy 路由、无前缀配置键)不在本计划内,仍按主计划书阶段 5 统一拆除。

---

## 设计决策

### D1:内核实体注册表(解决 C1、C2)

耦合根源是"回收站/导出器需要知道有哪些表"。注册表放**内核**而不是 recycle/json_transfer 各自 provide——因为注册动作发生在各插件 `activate()` 时,消费者可能还没加载,放内核无加载顺序问题;且"我有哪些数据实体"是通用元数据,不含业务逻辑,不违背内核业务无关原则。

`PluginAPI` 新增一个方法(协议新增,`api_version` 不变,纯增量):

```python
api.register_entity(
    entity="song",            # 实体类型 id(回收站里显示的类别)
    table="floating_songs",   # 表名
    label="歌曲",             # 回收站显示名
    export=True,              # 是否纳入 JSON 导出
    export_order=50,          # 导出/导入顺序(外键依赖决定先后)
)
```

- 内核只存注册信息(`plugin_manager` 或独立 `core/registry.py`),并提供 `api.list_entities()` 给消费者;
- **recycle 改造**:`ENTITY_TABLES` 删除,改为遍历 `list_entities()`;现有 12 个插件在各自 activate 里补注册调用,回收站行为不变;
- **json_transfer 改造**:这是最难的一处——导入时要做 id 重映射(旧 id → 新 id),现有代码对每张表有定制逻辑。改造方式:
  - 默认处理器:按注册信息做通用导出(整表按 project_id 过滤 dump)和通用导入(id 重映射映射表 + 外键字段按声明重写);
  - 需要定制行为的表(如有跨表引用、特殊序列化的),注册时允许插件传 `export_hook`/`import_hook` 函数;
  - 现有表的现有行为**逐张对照迁移**,以"导出-导入回环测试结果不变"为验收。
- 幂等与校验:重复注册同 entity 报错;表名仍受 `<id>__` 前缀约定约束(现有内置插件的历史表名豁免,协议中如实标注)。

### D2:前端扩展点 v1(解决 C3 的大头)

实现设计文档 §7.4 的最小子集,只先做两个扩展点:

- `sidebar.tabs`:右侧资料面板 tab。注册 `{id, title, icon?, render(el)/refresh(), visible?()}`。app.js 的 `switchRightTab` 改为遍历 `NW.getComponents("sidebar.tabs")`,不再出现 `OutlinePanel`/`CharacterPanel` 等具体名字;
- `toolbar.actions`:工具栏按钮(搜索/导出/回收站等)。注册 `{id, title, onClick}`。app.js 的工具栏改为渲染扩展点清单。

范围纪律(防止过度工程):

- 本期**只**消灭 app.js 里的组件名直引;组件之间的跳转(如 search-panel 点结果调 `Editor.loadChapter`)暂保留 window 别名,待 D3 事件化或阶段 5 处理;
- `Editor`/`Sidebar`(小说编辑器与目录树)是写作主区,不是"可插拔面板",本期不动——主区编辑器的插件化是更远的事,如实记录为已知边界;
- window 兼容别名继续保留(阶段 5 才拆),但 app.js 不再使用它们。

### D3:生命周期事件目录第一版(解决 C3 的长尾 + 为未来联动铺路)

内核/插件开始发出正式事件,替代剩余的"知道对方存在"式调用:

- `project.opened`(project 插件发出,payload: `{projectId, projectType}`)——面板刷新、编辑器加载改为订阅它;
- `project.closed`;
- 前端通过 `NW.events`(现有 AppState 总线)镜像同名事件,组件刷新逻辑从"app.js 点名调 refresh"改为"组件各自订阅事件"。

事件目录写入协议草案 §6,这是协议承诺的一部分,只增不改。

## 执行步骤与验收

### 步骤 1:内核注册表 + recycle 声明式改造

- 实现 `api.register_entity` / `api.list_entities`(内核,约 50~80 行);
- recycle 改为消费注册表;12 个插件补注册;
- **验收**:回收站功能回归(列出/恢复/删除各类型实体);符合性测试加用例:fixture 插件注册实体后出现在回收站查询里。

### 步骤 2:json_transfer 声明式改造

- 注册表驱动的导出/导入主循环 + 默认处理器 + hook 机制;
- 逐表迁移现有定制逻辑;
- **验收**:导出→导入回环测试(建项目、塞全类型数据、导出、导入、逐表比对行数与关键字段);符合性测试加用例:fixture 插件的表出现在导出 JSON 且导入后数据一致。

### 步骤 3:前端扩展点 v1

- `sidebar.tabs` + `toolbar.actions`;app.js 去组件名;
- 11 个被引用组件中属于面板/按钮的改注册式;
- **验收**:UI 行为不变(回归清单:tab 切换、按钮、快捷键);引导脚本加载的 fixture 前端能新增一个 tab 和一个按钮。

### 步骤 4:事件目录 v1 + app.js 去编排

- project 插件发 `project.opened/closed`;面板刷新改订阅制;app.js 中剩余的点名 refresh 清除;
- **验收**:切换项目后各面板刷新正常;app.js 中 grep 不到任何 `NW.plugins.<具体插件>` 引用。

### 步骤 5:协议草案更新

- 草案增补:`register_entity` API、扩展点清单(sidebar.tabs / toolbar.actions)、事件目录 v1;
- 标注 fixture 插件为"协议符合性参考"。

## 总验收(模拟第三方插件)

写一个测试插件 `plugins_demo/km_counter`(或放 tests/fixtures/):注册一张表 + 一个回收站实体 + 一个侧边栏 tab + 一个工具栏按钮 + 订阅 project.opened。**不改任何现有文件**,安装后:

- 新表数据能删进回收站并恢复;
- 导出 JSON 包含该表,导入副本数据一致;
- 侧边栏出现新 tab、工具栏出现新按钮;
- 切换项目时它收到事件。

通过即宣布 C1/C2/C3 消灭。

## 工作量与风险

| 步骤 | 预估 | 主要风险 |
|---|---|---|
| 1 实体注册表+recycle | 1 人日 | 低,纯重构 |
| 2 json_transfer 声明式 | 2–3 人日 | **最高**:id 重映射回环容易出数据级 bug,必须逐表比对验收 |
| 3 前端扩展点 | 1–2 人日 | 中,UI 回归靠手工 |
| 4 事件目录 | 1 人日 | 低 |
| 5 文档 | 0.5 人日 | — |

合计 **5.5–7.5 人日**。每步独立可提交,应用全程可用。

## 明确不做

- 不拆 window 兼容别名、不加路由前缀(主计划书阶段 5);
- 不动 script/floating_song/score 的插件化(主计划书阶段 3,MuseScore 推迟);
- 不做编辑器主区的插件化;
- json_transfer 对 score/floating_song 的惰性 import 暂留(那两个插件迁移时自然消解;若届时已声明式注册,改为消费注册信息)。
